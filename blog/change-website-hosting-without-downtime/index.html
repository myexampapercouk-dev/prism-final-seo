How to Move Website Hosting Without Downtime

How to change website hosting without downtime: plan the move, copy the site, test before DNS changes, lower TTL, protect email and check everything after.

By the Prism Works Studio team · 1 November 2026 · 7 min read

Key takeaways

  • Set up and test the site on the new host before changing DNS, so visitors keep seeing the old site until the new one is ready.
  • Lower your DNS TTL in advance and keep the old hosting running until the change has fully spread.
  • Map every DNS record, especially email records, before you move, so email and other services keep working.

Moving a website to a new host sounds risky, and done carelessly it can be: broken pages, missing images, lost emails and a site that disappears for a day. Done in the right order, though, visitors should not notice the switch. The trick is to build and test the new home completely before pointing anyone at it.

This guide walks through how to change website hosting without downtime for a typical self-hosted site, such as WordPress or WooCommerce. It also explains what is different if your site is on a hosted platform. If you are choosing a new host for WordPress, our WordPress hosting guide covers what to look for.

How visitors find your website

It helps to understand why downtime happens. Your domain name is just a label. When someone types it in, their device asks the Domain Name System (DNS) which server holds the site. DNS records, managed wherever your DNS is hosted, answer that question.

Changing hosting means changing those records to point at the new server. DNS answers are cached around the internet for a period set by each record's TTL (time to live). Until those caches expire, some visitors are sent to the old server and some to the new one. Downtime happens when the old server has already been switched off, or the new one is not ready, during that overlap.

So the whole method comes down to one principle: both servers must serve a working site for the entire changeover.

Step 1: Take stock before you start

Write down everything the current hosting provides. It is often more than the website:

  • The website files and database.
  • Email mailboxes, if they are hosted with the same provider.
  • DNS, if the host also manages your domain's records.
  • SSL certificates.
  • Scheduled tasks, server-level redirects and custom configuration.
  • Subdomains, such as a staging site or a separate shop.
  • Software versions, such as the PHP version a WordPress site runs on.

Also find out where your domain is registered and who has the login. If you cannot change DNS records, you cannot complete the move. Our ownership and handover guide explains why these accounts should be in the business's own name.

Step 2: Take a full backup

Before touching anything, take a complete backup of files and database and store it somewhere other than the current host. If anything goes wrong during the move, this is your safety net. Our website maintenance guide covers backups as part of routine care.

Step 3: Lower the DNS TTL in advance

A day or two before the move, lower the TTL on the records you will change, usually the A record for your domain and any www record. A shorter TTL means caches expire sooner, so when you do switch, the change spreads faster and the overlap is shorter. You will need to wait for the old, longer TTL to expire before the new short value takes effect, which is why this is done in advance.

Step 4: Set up the new hosting

Set up the new hosting account and match the environment to the old one as closely as is sensible: the same or a compatible software version, the same database settings and enough storage for your files. If you plan to upgrade versions as part of the move, consider doing that as a separate step later, so you are only changing one thing at a time.

Step 5: Copy the site across

Copy the files and import the database onto the new server. For WordPress, the site's address is stored in the database, and the configuration file holds database connection details, so both need checking after the copy. Many hosts offer migration tools or will migrate a site for you; whichever route you use, the testing steps below still apply.

On a shop or a site that takes bookings or form submissions, plan a short content freeze. Any orders or changes made on the old server after you copy the database will not exist on the new one. Choose a quiet time, copy the database as late as possible, and avoid editing content until the switch is complete.

Step 6: Test before anyone sees it

This is the step that avoids downtime. You want to view the site on the new server while the public still sees the old one. Common ways to do this include a temporary address provided by the new host, or editing the hosts file on your own computer so only your machine is sent to the new server. Your host's documentation will explain the options available.

Check thoroughly:

  • Every main page and template loads correctly.
  • Images, downloads and fonts appear.
  • Contact forms send and arrive.
  • Shop: products, basket, checkout and payment in test mode, plus order emails.
  • Logins for admin and customer accounts.
  • Redirects you rely on still work.
  • No error messages appear.

Fix anything that fails before moving on. Nothing has changed for visitors yet, so there is no pressure.

Step 7: Prepare SSL

Visitors expect a secure connection. Make sure the new host can issue or install an SSL certificate for your domain. Some certificates can only be issued once DNS points at the new server, which can mean a short gap; check with the new host how they handle this so you can plan around it.

Step 8: Map every DNS record, especially email

Before switching, list every DNS record that currently exists. Email depends on MX records and on authentication records such as SPF, DKIM and DMARC. Other services, such as site verification for Google tools or email marketing platforms, may rely on TXT or CNAME records.

If you are moving DNS management to a new provider as well as the website, recreate every record there first. A missing MX record can stop email arriving. If your email is staying where it is, make sure only the website records change.

Step 9: Switch DNS

When the new site is tested and records are ready, update the A record (and www) to point at the new server. Because you lowered the TTL, visitors should move over fairly quickly, but some caches may take longer. That is fine: the old server is still running and still serving a working site.

Step 10: Check, then wait before cancelling

Once the change has spread, repeat the tests on the live domain. Check that the SSL certificate is valid, forms and checkout work, and email is flowing in both directions. If you use Google Search Console, check for crawl errors over the following days.

Do not cancel the old hosting straight away. Keep it running for a while so stragglers on old DNS caches still see a working site, and so you can retrieve anything you missed. Before cancelling, take one final backup from the old server and download any email still stored there. Once you are happy, you can raise the TTL back to a normal value.

What if you are on Shopify, Wix or Squarespace?

On hosted platforms, the platform provides the hosting, so "changing hosting" usually means moving to a different platform altogether. That is a migration rather than a hosting move: content, URLs and design all change. The DNS principles above still apply when you point your domain at the new platform, but you also need redirects from old URLs to new ones to protect search rankings. Our SEO migration checklist covers that side.

Mistakes to avoid

  • Cancelling old hosting before DNS has fully switched.
  • Forgetting email records when moving DNS.
  • Copying the database early, then losing orders placed after the copy.
  • Testing only the home page.
  • Changing hosting, software versions and design all at once, making faults hard to trace.
  • Not knowing who holds the domain login until the day of the move.

A one-page move plan

Before you begin, it helps to write the move as a short plan that everyone involved can see. List the date and time of the switch, who is doing each step, how you will test, what will trigger a decision to switch back, and how long the old hosting will stay live. Switching back is simple while the old server is still running: point the DNS records back at it. Knowing that in advance takes much of the stress out of the day.

FAQs

Can I move hosting without any downtime?

For many sites, yes, if the new site is fully set up and tested before DNS changes and the old hosting stays live until the change has spread.

How long does a DNS change take to spread?

It depends on the TTL values and on how long other networks cache records. Lowering TTL in advance shortens it, but keep the old host running as a buffer.

Will moving hosting affect my SEO?

If the URLs and content stay the same and the site stays available, a hosting move on its own should not normally cause problems. A slower or unreliable new host could, so check speed after the move.

Will I lose my email if I change hosting?

Not if you plan for it. Identify where email is hosted, recreate MX and authentication records where needed, and move any mailboxes before cancelling the old account.

What about orders placed during the move?

Copy the database as late as possible, pick a quiet time and pause content changes until the switch is complete, so no orders are left on the old server.
